Lecture 6Overview

Multi-Agent Systems: Patterns & Orchestration

Eight ordinary Python functions, one shared dictionary, and twenty lines of wiring. A supervisor turns free text into structured fields; four specialists fan out to live APIs; cost, itinerary and final agents synthesise. There is no magic.

flowchart TD
  S([START])-->SUP["supervisor<br/>Gemini: text to JSON"]
  SUP-->FL["flight_agent<br/>Aviationstack"]
  SUP-->HO["hotel_agent<br/>Tavily"]
  SUP-->NE["news_agent"]
  SUP-->WE["weather_agent<br/>geocode then forecast"]
  FL-->CO["cost_agent<br/>Tavily + Gemini"]
  HO-->CO
  FL-->IT["itinerary_agent"]
  HO-->IT
  NE-->IT
  WE-->IT
  CO-->IT
  IT-->FI["final_agent"]
  FI-->E([END])

Every arrow is really "write to shared state, then let the next node read it" — no two specialists ever talk directly. cost_agent waits on two inputs, itinerary_agent on five, and that uneven fan-in is why the final agent runs twice.

L6 · Multi-Agent SystemsRungs 1–3

Shared state

A whiteboard in the middle of the office. Nobody passes notes; everybody reads and writes the board.

What it is

One TypedDict (TravelState) that every node reads from and writes into. A node returns only the keys it changed — {"flights": {...}} — and LangGraph merges that fragment in.

Why it exists

Agents need to share results without knowing about each other. A shared dictionary is the simplest channel that lets you add a ninth agent without touching the other eight.

Advantage

Each node stays ignorant of every other node’s keys, so you can unit-test one agent against a two-key dictionary. Adding an agent is additive, never a refactor.

Disadvantage

total=False makes every key optional, so missing data is invisible. TypedDict is documentation only — Python never enforces it, and an undeclared key fails silently downstream.

Use case

Any pipeline where several steps contribute different slices of one result: enrichment pipelines, ETL fan-out, multi-source research agents.

Test cell 15 runs hotel_agent against just {"destination": "Manali", "days": 5} — the whole agent needs two keys.
L6 · Multi-Agent SystemsRungs 1–3

Nodes and edges

A subway map. Stations are nodes, lines are edges, and your request can only travel where a line exists.

What it is

add_node(name, fn) registers a worker. add_edge(a, b) says "after a, b may run". compile() freezes the description into an executable graph.

Why it exists

It separates what each worker does from when it runs. Reorder the pipeline by editing edges; the agent functions never change.

Advantage

All orchestration for this 32-cell notebook lives in ~20 lines. Fan-out is free parallelism, the graph renders as a picture, and the dependency structure is inspectable before you run it.

Disadvantage

compile() snapshots the graph — edit a node, forget to recompile, and you silently run the old one. Uneven fan-in depth can schedule a downstream node more than once.

Use case

When the dependency structure is known and fixed. If the required steps vary per request, LLM tool-calling fits better.

Output shows 🎯 FINAL AGENT STARTED printed twice — uneven fan-in across supersteps, billing the largest prompt twice.
L6 · Multi-Agent SystemsRungs 1–3

Grounding

An open-book exam where the invigilator adds: if it is not in the book, write "not available".

What it is

Paste live API results into the prompt and add explicit rules. The itinerary prompt carries seven: do not invent live facts; do not claim a flight is bookable; clearly mark estimates…

Why it exists

A fluent model will happily invent a plausible flight number. Grounding converts "sounds right" into "supported by retrieved evidence, or declared absent".

Advantage

Turns the biggest LLM risk into a manageable one. The cost agent’s JSON shape even forces assumptions and source_notes arrays, so the reasoning is auditable.

Disadvantage

Costs prompt tokens on every call, and rules are advisory — a model can still drift. It also can’t detect stale data: nothing here timestamps the API responses.

Use case

Any user-facing system quoting prices, availability, medical or legal facts — anywhere a confident wrong answer is worse than "I don’t know".

Aviationstack returned flights to Patna, Leh, Mumbai, Varanasi. Final answer: "no direct flights" from DEL to Kullu — and recommends road transit instead.
L6 · Multi-Agent SystemsRungs 1–3

API-only vs LLM-backed agents

Researchers and writers. Don’t pay a writer’s price for a researcher’s job.

What it is

Four agents (flight, hotel, news, weather) make zero LLM calls — they are requests.get() with error handling. Four (supervisor, cost, itinerary, final) call Gemini.

Why it exists

LLM calls cost money, add seconds of latency, and can hallucinate. Use them only where judgement or language is required — never for fetching.

Advantage

Cuts cost and latency sharply, and the deterministic agents are trivially testable. The four API agents share no data, so they overlap in one superstep.

Disadvantage

Requires you to classify each step correctly up front. And one "agent" may be several HTTP calls — the weather agent geocodes, then fetches — so the boundary is responsibility, not requests.

Use case

Every agent pipeline. Ask of each node: does this need judgement, or just data? Only the first kind earns a model call.

Weather agent: geocode "Manali" → (32.2455, 77.1873), then fetch forecast. Two calls, one responsibility.
L6 · Multi-Agent SystemsRung 4 · Staff lens

Multi-Agent Orchestration — judging it

Where it breaks at scale

Third-party rate limits run out before compute. One request fans out to five APIs; 100 concurrent requests is 500 external calls, and Aviationstack’s free tier caps in the hundreds per month. No retry, no backoff, no per-node timeout.

Latency & cost budget

Wall clock ≈ supervisor + max(4 research) + cost + itinerary + final. Token cost is dominated by the last two calls, which paste the entire accumulated state — and one of them is billed twice.

The real trade-off

You are buying per-step debuggability and parallelism by paying orchestration complexity and extra LLM calls. The alternative — one call with five registered tools — is simpler and cheaper but untestable per step.

Silent failure modes

Ranked by quietness: stale data presented as live → state.get("days", 1) silently defaulting → duplicate node execution → empty IATA silently widening the query.

Why an interviewer asks

A litmus test for whether you think in dependency graphs or scripts. The follow-up is always partial failure: "the hotel API is down — what does the user see?" Today: the run dies.

CrewAI & Microsoft AutoGen Frameworks

An agent is an LLM call wrapped with a name, a system message, and a way to send and receive messages. A multi-agent system is several of those sharing messages under simple, explicit rules. Five FinTrack analysts debate a launch — all built from the same config, differing only in system message.

  participant FA as Finance_Analyst

  MGR->>MA: your turn + FULL history

L7 · CrewAI & AutoGenRungs 1–3

The agent is its system message

Five identical actors, five different scripts.

What it is

Every analyst is AssistantAgent(name, system_message, llm_config). Same model, same settings — the system message alone produces the personality, responsibilities and stance.

Why it exists

You need genuinely different perspectives without building five different systems. The system message is the cheapest possible specialisation mechanism.

Advantage

Adding a sixth analyst is one object. Each message carries role + responsibilities + stance — and stance is what stops five agents politely agreeing.

Disadvantage

Personality is only as reliable as prompt adherence; a model can drift out of role. And length discipline must be enforced manually in every message.

Use case

Design review panels, red-team vs blue-team analysis, any decision needing deliberately opposed viewpoints.

Product Manager is told "Do NOT simply agree with everyone"; every message ends "Keep every message to 2-4 sentences" — a context-budget control, not style.
L7 · CrewAI & AutoGenRungs 1–3

Tool calling vs code execution

A vending machine versus a kitchen. Fixed buttons, or cook anything.

What it is

Tool calling: pre-register one safe function with two decorators — register_for_llm advertises it, register_for_execution runs it. Code execution: the model writes Python and a LocalCommandLineCodeExecutor runs it as a subprocess.

Why it exists

LLMs are unreliable at exact arithmetic, lookups and queries. Hand that work to real code and the answer stops being a guess.

Advantage

Tool calling gives a tiny, audited attack surface and exact results. Code execution handles problems you can’t express as one predefined function.

Disadvantage

Register only one decorator and the tool is either never called or never executed. Code execution is arbitrary code on your machine — fine in a disposable Colab VM, unshippable as a service.

Use case

Tool calling for maths, DB lookups, pricing, API calls. Code execution for open-ended data manipulation — behind a real sandbox.

Gemini emits calculate_roi(revenue=150000, cost=50000) → (150000−50000)/50000×100 = 200.0%. Exact, not predicted.
L7 · CrewAI & AutoGenRungs 1–3

Reflection

A first draft, a red pen, and a rewrite.

What it is

Three calls with different system messages: Writer drafts, Critic names what’s missing (privacy, accuracy, cost), Writer rewrites given both its draft and the critique.

Why it exists

First drafts are confident and incomplete. A separate critique pass surfaces the omissions the drafting pass is blind to.

Advantage

No framework feature needed — three ordinary calls and an f-string. The revised output is visibly more hedged and more complete.

Disadvantage

3× the cost and 3× the latency of a single answer. A same-model critic shares the generator’s blind spots, so it catches slips and misses systematic errors.

Use case

When quality matters more than latency: generated code, customer-facing copy, anything reviewed before it ships.

Compare DRAFT vs REVISED in cells 20-22 — the revision addresses privacy and accuracy the confident one-liner ignored.
L7 · CrewAI & AutoGenRungs 1–3

GroupChat

A whiteboard nobody is allowed to erase.

What it is

GroupChat(agents, messages, max_round=11, speaker_selection_method="round_robin") plus a GroupChatManager. A shared message history and a turn-taking rule — that is the whole mechanism.

Why it exists

One-on-one chats are isolated pairs; no agent can react to what another said. Shared history is what converts parallel monologues into an argument.

Advantage

Every agent sees everything, so they genuinely agree, disagree and build on each other. round_robin is reproducible — ideal for demos and tests.

Disadvantage

Token cost grows quadratically (O(A·R²)) because every round resends the full history. Latency is fully serial. max_round stops on a turn count, so it can cut off mid-argument.

Use case

High-stakes decisions warranting adversarial review. For a low-stakes summary, one well-prompted call is the right call.

5 agents × max_round=11 ≈ 11× the calls of a single agent — and each call carries a larger prompt than the last.
L7 · CrewAI & AutoGenRung 4 · Staff lens

AutoGen Multi-Agent — judging it

Where it breaks at scale

Context window, quadratically. With A agents over R rounds you send O(A·R²) tokens. The failure is quiet — the model truncates or loses the middle of a long prompt rather than erroring. The "2-4 sentences" rule is a context-budget control.

Latency & cost budget

GroupChat is ~11× a single agent on call count and priciest per call. Round-robin means no two agents ever generate concurrently — wall clock is the sum of 11 completions, though the four analysts have no data dependency in round 1 and could be fanned out.

The real trade-off

You are buying genuine multi-perspective disagreement by paying quadratic tokens and serial latency. One call prompted to "consider four angles" costs a tenth — but a single model self-critiquing converges on one voice.

Silent failure modes

Manufactured consensus (defended against explicitly here) → silent context truncation → max_round hit mid-argument → substring control flow like "DONE" in content matching "I’m not DONE yet".

Why an interviewer asks

A litmus test for whether you can justify the agent count. Start from one call and make each extra agent earn its 2-4× cost. The staff follow-up is always: "what stops it?"

Lecture 8Overview

Advanced Agent Patterns: ReAct, Reflection & Memory

Three patterns that turn a chatbot into an agent: ReAct lets it act, Reflection lets it self-correct, Memory lets it persist. ReAct is the star — asked to reorder a cancelled order, the agent discovers Status: Cancelled and reports it. Nobody wrote that branch.

stateDiagram-v2
  [*] --> Thought: user query
  Thought --> Action: emit tool_calls
  Action --> Observation: ToolMessage returns
  Observation --> Thought: enough info?
  Thought --> Answer: yes
  Answer --> [*]

The arrow from Observation back to Thought is what separates ReAct from planning: the agent re-decides after seeing what actually returned, rather than executing a plan written up front. Adaptability comes from observing after every action, not from planning better.

L8 · ReAct, Reflection & MemoryRungs 1–3

The ReAct loop

A detective. Form a hunch, check one fact, let the fact change the hunch.

What it is

Thought (reason about what’s needed) → Action (call a tool) → Observation (read the result) → repeat until it can answer. In LangGraph: an AIMessage with tool_calls, then a ToolMessage.

Why it exists

Chain-of-Thought can’t touch external data; Plan-and-Solve commits to a plan before seeing any results. ReAct adapts after every single step.

Advantage

Strongest error recovery of the three patterns. Handles branches nobody coded — cancelled orders, out-of-stock items, missing records.

Disadvantage

Latency is serial in turns and the step count is unbounded without a cap. Every step resends the full history, so long loops silently blow the context window.

Use case

Open-ended research, customer support over live systems, debugging — anywhere the next step genuinely depends on what came back.

Query 3 makes 4 tool calls — it cannot know to look up "Noise Cancelling Headphones" until lookup_order("1003") returns.
L8 · ReAct, Reflection & MemoryRungs 1–3

Tools — the docstring is the interface

A job advert. The model only applies for tools whose advert describes its problem.

What it is

@tool turns a plain function into something the LLM can call, and the docstring becomes the description the model reads. All three here follow: what it does → what it returns → when to use it.

Why it exists

Tool selection is a reading-comprehension task. The docstring is the entire brief the model gets, so a vague one is a broken tool.

Advantage

Zero ceremony — a decorator and a good docstring. Tools returning helpful error strings (not exceptions) let the agent recover instead of crashing the loop.

Disadvantage

All descriptions sit in the prompt on every iteration, so 40 tools consume the budget repeatedly and selection accuracy falls — silently, as plausible-but-wrong picks.

Use case

Every tool you ever write. At scale, retrieve the top-5 relevant tools per query instead of listing all of them.

lookup_order("9999") returns "Error: No order found… Valid order IDs are: [...]" — text the agent can read and recover from.
L8 · ReAct, Reflection & MemoryRungs 1–3

Reflection: generate → judge → revise

Submitting code for review, then pushing a fix.

What it is

Three one-line functions wrapping the same model with different system messages, looping up to max_iterations=3, exiting early when the critique contains LGTM.

Why it exists

A generator optimises for producing something; a judge optimises for finding what’s wrong. Splitting the roles surfaces problems one pass misses.

Advantage

Returns a full history plus approved: True/False, so callers can distinguish "the judge signed off" from "we ran out of attempts". Cell 38 even execs the result and unit-tests it.

Disadvantage

Up to 7 calls for one answer. "LGTM" in critique would accept "this is not LGTM yet". Architecture 1 (same model judging itself) is blind to its own systematic errors.

Use case

Generated code, structured extraction, anything with a checkable spec. Use a separate, stronger judge model when the stakes justify it.

In this run the judge replied LGTM. at iteration 1 — so the revise path never executed. You saw the structure, not the payoff.
L8 · ReAct, Reflection & MemoryRungs 1–3

Three types of memory

What’s on your desk, what you remember about this colleague, and the company wiki.

What it is

Short-term = the current prompt/context window. Episodic = conversation history across sessions (last 10 turns). Long-term = a persistent vector store searched by embedding similarity.

Why it exists

Context windows are finite and sessions end. Without the other two, an agent starts every conversation as a stranger.

Advantage

Retrieval (top_k=3, similarity > 0.5) compresses an unbounded store into a prompt-sized slice, so the agent can "remember" far more than it can hold.

Disadvantage

Taught as pseudocode only — nothing runs here. Retrieval recall becomes the hard ceiling on what can ever be recalled, and stale memories are never invalidated.

Use case

Personal assistants, long-running support threads, any agent expected to improve across sessions rather than restart cold.

The key insight: retrieval turns long-term memory into short-term memory. The store is huge; the window is not.
L8 · ReAct, Reflection & MemoryRung 4 · Staff lens

ReAct, Reflection & Memory — judging it

Where it breaks at scale

Unbounded steps, each resending everything. Query 3’s fourth request carries all three prior observations; with verbose tool outputs a ten-step loop hits the window and the model starts ignoring early observations rather than erroring. Tool count is the second limit — 30 tools degrade selection.

Latency & cost budget

Every step is a full model round trip; the tools here are dictionary lookups costing microseconds. The model dominates, the tools are free — optimising the tool is optimising the wrong thing. Reflection multiplies: max_iterations=3 is up to 7 calls.

The real trade-off

ReAct buys adaptability by paying serial latency and an unpredictable bill. Plan-and-Solve gives you a known cost and concurrent dispatch but cannot recover when step 2 surprises it. Mature answer: plan when the structure is knowable, react when it isn’t.

Silent failure modes

Substring control flow shipping unreviewed code → self-review blindness → silent context truncation → loop exhaustion read as success → exec() on model output.

Why an interviewer asks

A litmus test for whether you know where the loop terminates. The staff probe: "your judge approved first try — is the code good?" Recognising an unexercised branch as a risk is the judgement being tested.

Playwright gives an agent eyes and hands. browser-use gives it a chauffeur who can read road signs. After demoing the full autonomous agent, the notebook quietly goes back to deterministic scraping plus one structuring call — because once you know the page, autonomy is the expensive option.

L9 · Browser AutomationRungs 1–3

Browser → Context → Page

The Chrome process, an incognito window, a tab.

What it is

Browser = the whole process (expensive; start once). Context = an isolated window with its own cookies, storage and identity (cheap). Page = one tab inside a context.

Why it exists

You need many simultaneous identities without paying for many browsers. The context is the layer that makes that possible.

Advantage

Five contexts in one process = five logged-in identities in parallel with no cookie bleed. This is Playwright’s whole parallelism story.

Disadvantage

Get the layer wrong and you OOM at trivial concurrency — a browser is 100-300 MB resident, a context only tens. Pages inside one context share cookies, silently breaking isolation.

Use case

Any multi-account scraping, parallel test suites, or per-user automation. Set storage_state and user_agent on the context.

4 GB box, 12 logged-in sessions → 1 browser + 12 contexts. Twelve browsers OOMs; twelve pages shares one cookie jar.
L9 · Browser AutomationRungs 1–3

Locators & auto-wait

"The blue Login button" survives a redesign; "third div, second span" does not.

What it is

Stability ranking: role → text/label → data-testid → CSS class → XPath. Before any click Playwright checks five things — attached, visible, stable, receiving events, enabled — retrying until they pass or the 30 s timeout expires.

Why it exists

Modern class names are build-generated hashes that change every deploy, and modern pages render asynchronously. Both break naive automation.

Advantage

Auto-wait means the LLM never reasons about page-load timing — it just says "click element 7". Role locators match how a human (and an LLM reading the accessibility tree) describes a page.

Disadvantage

Auto-wait can mask a genuinely missing element until the timeout. networkidle is a trap — commercial sites never idle, so it times out or returns early.

Use case

Prefer get_by_role everywhere. When you need explicit control, wait on a specific selector or URL pattern — never on network quiet.

Infinite scroll: 8 iterations × 1.2 s wait, stop when the count stops changing → 50 quotes loaded. The cap is not optional.
L9 · Browser AutomationRungs 1–3

Authentication patterns

The "Remember me on this device" checkbox.

What it is

Pattern 1 — storage_state: log in once by hand, save cookies + localStorage to JSON, reload it on every later run. Pattern 2 — programmatic login: fill the form in code, then save the state anyway.

Why it exists

Logging in from scratch every run is slow, trips anti-bot heuristics, and may trigger 2FA you cannot automate past.

Advantage

You start already authenticated, at zero cost per run. Combining both patterns gives you rotation and reuse.

Disadvantage

That JSON file is a live credential — anyone holding it can act as you, no password needed. At scale it becomes a secrets-management problem with rotation and audit.

Use case

Pattern 1 for a stable personal/service account. Pattern 2 for rotating accounts or fresh onboarding flows.

.gitignore it, encrypt it in production. Leak means account takeover, not a data breach.
L9 · Browser AutomationRungs 1–3

How the LLM sees a page

A numbered menu, not a wall of HTML.

What it is

DOM mode (default): walk the DOM, drop invisible elements, emit a numbered list — [1]<button>Sign in</button>. Vision mode: screenshot with numbered bounding boxes, sent to a vision model.

Why it exists

Raw HTML is enormous and mostly irrelevant. A numbered list of interactive elements is the smallest representation that supports a decision.

Advantage

DOM mode is fast, token-cheap and works with text-only models. The constrained action space means the model cannot hallucinate a CSS selector — its only options are numbers it was just shown.

Disadvantage

DOM mode is blind to visually-encoded meaning (charts, canvas apps). Vision mode costs thousands of image tokens per step, multiplied across the whole loop.

Use case

DOM mode by default. Vision only for visually complex apps — Canva, Figma — where the DOM is uninformative.

use_vision=False here because Groq’s openai/gpt-oss-120b is text-only.
L9 · Browser AutomationRung 4 · Staff lens

Browser Automation — judging it

Where it breaks at scale

Memory runs out fast — a Chromium process is 100-300 MB before loading anything, so a 4 GB worker runs ~10-20 contexts and one browser. The harder limit is the target site: rate limits, CAPTCHAs and IP bans arrive long before your CPU does.

Latency & cost budget

Agent path: 1 LLM call per step × max_steps=8, serial. Scrape path: exactly 1 call. Roughly an order of magnitude apart. Browser startup is the fixed floor on both — launch once, reuse contexts.

The real trade-off

The agent buys tolerance of unknown, changing pages by paying ~10× cost, high latency and non-determinism. The decision rule is change frequency, not difficulty: automate deterministically when the page is stable and you run it repeatedly.

Silent failure modes

All silent: selector rot returning zero rows as "success" → partial page capture → agent hitting max_steps and returning a plausible partial answer → session expiry scraping the logged-out page.

Why an interviewer asks

A litmus test for whether you reach for the heaviest tool first. API? Static HTML? Only then a browser. The staff probe is maintenance: "this runs nightly for two years — what breaks?" Answer: assert on expected row count.

LlamaIndex & Advanced RAG Frameworks

A working RAG pipeline is five lines. Everything after that is choosing the right kind of index for the question you are asking — and this notebook builds four over the same documents, letting each one visibly succeed and visibly fail.

  N-->T["TreeIndex<br/>LLM summaries"]
  N-->K["KeywordTableIndex<br/>exact terms"]

L10 · LlamaIndex & RAGRungs 1–3

The RAG pipeline

An open-book exam where a research assistant finds the right pages before you start writing.

What it is

Documents → chunks (nodes) → embeddings → index → query engine. At question time: embed the question, retrieve the nearest chunks, paste them into the prompt, generate.

Why it exists

An LLM’s knowledge is frozen at training time and has never seen your internal documents. RAG fixes both by supplying the relevant text at question time.

Advantage

Each stage is one object you can swap. Embeddings run locally on CPU here, so embedding is free and no document text leaves the machine — cheap and data-residency compliant.

Disadvantage

Nothing updates. A changed policy means rebuilding the whole index, and at scale that becomes a change-data-capture problem rather than a notebook cell.

Use case

Internal documentation Q&A, support knowledge bases, policy lookup — any corpus the model was never trained on.

The debugging habit: read response.source_nodes first. Right chunks + wrong answer = generation bug. Wrong chunks = retrieval bug.
L10 · LlamaIndex & RAGRungs 1–3

Chunking

Tearing a book into index cards. Too small loses context; too big matches nothing sharply.

What it is

SentenceSplitter(chunk_size=512, chunk_overlap=50) cuts on sentence boundaries at ~512 characters, repeating the last 50 characters of each chunk at the start of the next.

Why it exists

Chunks are the atoms of retrieval. If an answer spans three chunks, no amount of clever retrieval reassembles it.

Advantage

Overlap stops a fact stated across a boundary from being lost to both chunks — a little storage buys robustness at the seams.

Disadvantage

The highest-leverage knob and the least principled one: there is no defensible way to pick 512 and 50 except measuring against a labelled eval set. Get it wrong and everything downstream inherits the damage.

Use case

Tune per corpus. Dense policy text wants smaller chunks; narrative documents want larger ones with more overlap.

A 1,200-character document yields ≈ 1200 ÷ (512−50) ≈ 3 chunks, each sharing a 50-character seam.
L10 · LlamaIndex & RAGRungs 1–3

Four index types

Four librarians. Each is brilliant at one request and useless at another.

What it is

Vector groups by meaning. Tree summarises bottom-up. Keyword indexes exact terms. Graph tracks who relates to whom, via LLM-extracted triplets.

Why it exists

There is no universal index. Each organises the same chunks around a different question shape, and the shape of your questions decides which you need.

Advantage

Build several over one corpus and route between them. Vector is cheap to build; keyword is instant for identifiers; graph answers relationship questions nothing else can.

Disadvantage

Tree summarises the detail away. Keyword has no notion of "close enough". Graph costs one LLM call per chunk to build — economically absurd on a large corpus.

Use case

Vector as default; keyword alongside it for IDs and acronyms; tree for "summarise everything"; graph only when relationship questions are a recurring workload.

Keyword index asked about "reward points" → Empty Response. The document says "loyalty points". Exact match has no synonyms.
L10 · LlamaIndex & RAGRungs 1–3

QueryEngineTool — the hinge to agentic RAG

A receptionist with a directory of specialists.

What it is

Wrap each query engine as a tool with a name and a description. A planner LLM then decides which knowledge source answers which part of a compound question.

Why it exists

Once you have several corpora or several index types, something must route. Encoding each engine’s competence as a description makes routing an LLM-readable decision.

Advantage

The planner needs no knowledge of the underlying index — only what each tool is good at. This is precisely the step from "RAG pipeline" to "agent with retrieval tools".

Disadvantage

The description is the only thing the router reads, so routing quality is entirely prompt quality. Overlapping descriptions produce confidently wrong routing, silently.

Use case

Multi-domain assistants: Tesla docs vs Netflix docs vs OpenAI docs; or policy vs incidents vs code within one company.

The notebook states the rule plainly: "Good tool descriptions improve tool selection." That is the whole lever.
L10 · LlamaIndex & RAGRung 4 · Staff lens

LlamaIndex & RAG — judging it

Where it breaks at scale

SimpleVectorStore is a Python list scanned linearly — O(N) per query, entirely in RAM, lost on restart. Replaced by an ANN index (HNSW/FAISS/Chroma/pgvector) through StorageContext. KnowledgeGraphIndex breaks sooner: one LLM call per chunk, non-incremental.

Latency & cost budget

Build-time and query-time have different shapes. Embedding is free (local CPU BGE, 133 MB). Query latency is dominated by the single Groq completion, not retrieval — so chasing retrieval speed on a small corpus optimises the wrong thing.

The real trade-off

A local small embedding model buys zero marginal cost and data residency by paying retrieval quality — bge-small is 384-dim and English-only. The deeper trade is the index choice itself: you are choosing which question shape to be good at.

Silent failure modes

Garbage corpus → garbage chunks (demonstrated here by accident) → stale index answering from last month’s policy → Settings drift after construction → Empty Response misread as "no such policy".

Why an interviewer asks

A litmus test for whether you debug retrieval or blame the model. Reaching for source_nodes first — and splitting the bug into retrieval vs generation — is the clearest signal of having operated a RAG system.

Agentic RAG & GraphRAG

One question breaks plain RAG: "which engineering managers have team members working on projects involving LLM security?" Vector search returns the right documents (0.589 / 0.522 / 0.448) and still cannot answer — because the answer is a path, not a passage.

flowchart LR
  DOC["Guardrail Overview<br/>cosine 0.589"]-->|ABOUT|PRJ[Project Guardrail]
  ANA[Ana Iyer]-->|WORKS_ON|PRJ
  FAT[Fatima Zahra]-->|WORKS_ON|PRJ
  ANA-->|REPORTS_TO|ELE["Elena Duarte<br/>is_engineering = 1"]
  FAT-->|REPORTS_TO|ELE
  BEN[Ben Cho]-->|WORKS_ON|SEN[Project Sentinel]
  BEN-->|REPORTS_TO|SOF["Sofia Klein<br/>is_engineering = 0"]

Vector search gets you as far as the leftmost box and stops — there is no edge inside an embedding to follow from a document to the people who work on it. Elena is the answer; Sofia is the trap — she manages people on these very projects, and only the is_engineering = 0 property excludes her.

L11 · Agentic RAG & GraphRAGRungs 1–3

Why traditional RAG fails

A library catalogue finds books about a topic; it cannot tell you who reports to whom.

What it is

RAG works when the answer is already written somewhere. It struggles when the answer must be computed by joining, filtering, traversing and aggregating.

Why it exists

Those four verbs are your diagnostic checklist — run them against a question before choosing an architecture, not after the retriever disappoints.

Advantage

Gives you a one-line test. "What does Guardrail do?" needs none of the four → RAG is fine. "Which engineering managers…?" needs traverse + filter → you need a graph.

Disadvantage

The failure is deeply counter-intuitive because retrieval succeeds — the top-3 are all genuinely about LLM security. A working retriever can still be the wrong tool.

Use case

Apply before every RAG project. If any of the four verbs appear, plan for a second retrieval modality from day one.

Top-3 by cosine: Guardrail 0.589 · Sentinel 0.522 · Model Input Security Policy 0.448 — all relevant, none containing a manager’s name.
L11 · Agentic RAG & GraphRAGRungs 1–3

The property graph

The org chart, but every arrow is labelled and every box has fields.

What it is

Five node types (Employee, Department, Skill, Project, Document) and six edge types (REPORTS_TO, WORKS_ON, ABOUT, HAS_SKILL, PART_OF, OWNED_BY). Nodes carry properties.

Why it exists

Relationships are first-class data. A graph makes "follow this edge" an O(1) operation instead of something you hope an embedding encoded.

Advantage

Answers multi-hop questions nothing else can. NetworkX gives you the model for free in memory; Neo4j adds indexed adjacency, persistence and Cypher when you outgrow it.

Disadvantage

In-memory traversal scans all edges — O(E) per hop. And somebody must build and maintain the graph: entity types, relationships, and properties like is_engineering staying accurate as people change roles.

Use case

Org hierarchies, supply chains, dependency graphs, fraud rings, medical ontologies — any domain where "how are these connected?" is a routine question.

Sofia Klein manages people on Guardrail and Sentinel. Only is_engineering = 0 excludes her. Delete that one field and the system is confidently wrong.
L11 · Agentic RAG & GraphRAGRungs 1–3

The planner

A project manager writing the task list before anyone starts work.

What it is

An LLM decomposes the question into ordered subquestions, each tagged with exactly one tool — sql, vector or graph — returned as JSON. It executes nothing.

Why it exists

Complex questions need different retrieval modes for different parts. Deciding which, per question, is a reasoning task — so give it to the model.

Advantage

Separating planning from execution means you can inspect, validate, log or override a plan before paying for a single call. At plan time those tool names are just strings.

Disadvantage

A single point of failure with no schema enforcement — a hallucinated tool name or a subquestion referencing evidence no earlier step produced fails at execution, not at plan time. Plans can also contain redundant steps.

Use case

Any system with more than one retrieval backend. Constrain the planner with a strict enum and validate the plan as a DAG before executing.

Plan: q1 vector (find LLM-security projects) → q2 graph (employees + managers) → q3 graph (keep engineering only).
L11 · Agentic RAG & GraphRAGRungs 1–3

Route → Execute → Reflect → Synthesize

Dispatch each task to the right specialist, collect results on one desk, check the desk is complete, then write the report.

What it is

Map each subquestion’s label to a real function, run it, deposit results in the evidence buffer, ask whether the evidence is sufficient, then make one LLM call to write the answer.

Why it exists

A plan is inert until something executes it — and something must decide whether the result is good enough to answer from.

Advantage

The evidence buffer is how step 2 knows what step 1 found. Reflection gives the loop a chance to retry before committing to a bad answer.

Disadvantage

Steps run strictly in order even when independent — a DAG-aware executor could parallelise. And a reflector that always returns sufficient is indistinguishable from no reflector.

Use case

Multi-source research agents, compliance queries spanning documents and databases, anything needing evidence from more than one system.

q1 → [Atlas, Guardrail, Sentinel] · q2 → [Elena Duarte] · q3 → [Elena Duarte] · reflection sufficient = True on the first pass.
L11 · Agentic RAG & GraphRAGRung 4 · Staff lens

Agentic RAG & GraphRAG — judging it

Where it breaks at scale

The planner is a single point of failure with no schema enforcement. Validate plans as a DAG before executing. The in-memory graph scans all edges per hop — O(E) — and must fit one process; Neo4j gives indexed adjacency. Deep plans blow the context window and latency together.

Latency & cost budget

Two LLM calls bracket a pipeline whose retrieval is essentially free — embedding + dot product over 20 rows, and in-memory edge scans, are microseconds. So optimise the calls, not the traversal: cache plans by question template, and trim what enters the synthesis prompt.

The real trade-off

You buy multi-hop correctness by paying two LLM calls and a hard dependency on graph data somebody must maintain. A bigger, better single retrieval is cheaper and simpler — and still cannot invent an edge that is not in the text.

Silent failure modes

Over-retrieval at step 1 poisoning every later hop (q1 returned Atlas, a data platform) → stale graph properties → reflection rubber-stamping → fallback mode read as live mode → redundant plan steps.

Why an interviewer asks

A litmus test for whether you classify a question before choosing an architecture. The staff probe is data ownership: "where does the graph come from, and who keeps it correct?" You have quietly acquired a data-quality SLA.

Lecture 12Overview

Hybrid Search & Advanced Retrieval

Last lecture the agent was the manager; this one upgrades the employee. The single top-k lookup becomes a stack: BM25 + dense fused by rank, a cross-encoder reranking the shortlist, a calibrated gate, an LLM verifier, and a capped retry loop. Retrieval in production is a mini-agent.

flowchart TD
  Q[User query]-->EXP{"confidence low?<br/>expand query"}
  EXP-->|3 LLM variants|BM["BM25<br/>exact terms, IDF"]
  EXP-->DEN["Dense bi-encoder<br/>384-dim"]
  BM-->|ranked list|RRF["RRF fusion<br/>1/(60+rank)"]
  DEN-->|ranked list|RRF
  RRF-->|shortlist 10-20|CE["Cross-encoder rerank"]
  CE-->GATE{confident?}
  GATE-->|no|ABST[abstain / retry]
  GATE-->|yes|VER{verifier:<br/>sufficient?}
  VER-->|insufficient|RETRY["reformulate<br/>max_iters=3"]
  RETRY-->EXP
  VER-->|sufficient|GEN[LLM synthesis]

Read it as a funnel that gets more expensive at every step: BM25 and the bi-encoder are milliseconds over the whole corpus; the cross-encoder costs hundreds of milliseconds over ten documents; the verifier is a full LLM call over three. Never let an expensive stage see more than a shortlist.

L12 · Hybrid SearchRungs 1–3

BM25 — rare words win

A librarian who notices unusual words. Everyone says "the"; almost nobody says "INC-2847".

What it is

Scores a document by how many query terms it contains, weighted by each term’s IDF (how rare it is corpus-wide), with a length correction so long documents don’t win by size.

Why it exists

Users type exact identifiers, error codes and acronyms constantly, and those are precisely what semantic search blurs away.

Advantage

Decisive on exact terms, cheap, interpretable, and needs no training. Rare tokens dominate the score exactly as you want.

Disadvantage

No concept of synonymy at all. Paraphrase the query and it collapses — it ranked Access Request Procedure above the relevant document.

Use case

Identifier lookup, code search, legal citations, SKU and ticket numbers — anywhere users paste an exact string.

INC-2847 is in 1 of 20 docs → BM25 scores the right postmortem 4.501, the next two 1.553. Tokenise with the hyphen or it splits into inc + 2847.
L12 · Hybrid SearchRungs 1–3

Dense retrieval (bi-encoder)

A colleague who knows what you meant but cannot remember the ticket number.

What it is

Embeds the query and each document independently, then compares by cosine. Document embeddings are precomputed once and stored.

Why it exists

Users describe problems in their own words. Meaning-based matching bridges the gap when vocabulary does not overlap.

Advantage

Scales to millions — one query embedding plus a matrix multiply. Handles paraphrase and synonymy that BM25 cannot touch.

Disadvantage

Each document was compressed to a single vector before the query was known, so exact identifiers get averaged into generic "incident-ness". Nearly a coin flip on ID queries.

Use case

Natural-language questions, support search, discovery — paired with BM25, never alone.

On INC-2847 postmortem: correct doc 0.503 vs wrong postmortems 0.466 and 0.402. Technically right, almost a tie.
L12 · Hybrid SearchRungs 1–3

Reciprocal Rank Fusion

An Olympic medal table. You don’t add race times across sports; you add finishing positions.

What it is

RRF(d) = Σ 1/(k + rank) with k = 60. Combines ranked lists using only positions — the formula contains no reference to scores.

Why it exists

BM25 is unbounded and query-dependent; cosine sits in [−1, 1]. Any weighted sum needs a normalisation that is fragile and shifts per query.

Advantage

Scale-invariant by construction — no normalisation, no tuning, no training. Appearing in both lists is worth far more than a slightly better position in one.

Disadvantage

Discards score magnitude, so a crushing win and a narrow one count the same. k is a fudge factor chosen by convention rather than derived.

Use case

Any time you fuse rankers with incomparable scores — sparse + dense, multiple query variants, several models voting.

Rank 1 in both lists: 1/61 + 1/62 = 0.03252. Rank 3 in one list only: 1/63 = 0.01587. Roughly 2× — that is the robustness.
L12 · Hybrid SearchRungs 1–3

Cross-encoder reranking

The resume screener versus the interviewer.

What it is

Feeds query and document into one model together and outputs a single relevance score, applied only to a shortlist of 10-50 candidates.

Why it exists

A bi-encoder never sees query and document at the same time. A cross-encoder attends to their interaction — which is where the accuracy comes from.

Advantage

Substantially more accurate on the shortlist. And its cost is invariant to corpus size — 20 candidates whether you have 20 documents or 20 million. That invariance is the point of two-stage retrieval.

Disadvantage

N forward passes for N documents, so it can never be first-stage. Latency scales linearly with shortlist size, and scores are uncalibrated logits — often negative.

Use case

Stage 2 of every serious retrieval system. Airbnb-style: cheap retrieval narrows 500k listings to 300, then a heavy ranker reorders the top 50.

Measured: shortlist 5 → 165 ms · 10 → 246 ms · 20 → 452 ms. Roughly linear — which is why 20-50 is the industry range.
L12 · Hybrid SearchRungs 1–3

Abstention & the verifier

Stack Overflow’s "no results found" — a UX decision, not a bug. And Toyota’s andon cord.

What it is

A calibrated score threshold gates low-confidence results, and an LLM verifier sitting between retrieval and generation rules sufficient or insufficient on the retrieved snippets.

Why it exists

Every retriever always returns something. Without a gate, a corpus with no answer still produces five confident-looking documents and a fluent wrong answer.

Advantage

The verifier works well here and returns a reason, not just a verdict — and it costs only ~50-200 ms, cheap insurance against an incident.

Disadvantage

The score gate silently failed in this very notebook — 10 calibration pairs with overlapping ranges produced a threshold that never fires. A gate you trust that never fires is worse than no gate.

Use case

Support bots and compliance search, where a confident wrong answer is far worse than "I don’t know". In exploratory search UIs, imperfect results may beat a blank page.

Threshold −11.07; nonsense "time travel" query scored −10.95 → status: "ok". The gate did not fire.
L12 · Hybrid SearchRung 4 · Staff lens

Hybrid Search & Advanced Retrieval — judging it

Where it breaks at scale

Everything here is a linear scan, each breaking at a different size. BM25Okapi → a real inverted index. DOC_MATRIX @ q → an ANN index, accepting 95-99% recall for sublinear search. The cross-encoder never breaks — it only ever sees the shortlist.

Latency & cost budget

Reranking dominates and scales linearly with shortlist size (165/246/452 ms for 5/10/20). Worst case per query: 1 expansion call + N retrievals + rerank + verify + retry ×3 — which is why every one of those is gated or capped.

The real trade-off

Each layer buys accuracy by paying latency; the last two buy honesty. The threshold and verifier purchase the ability to say "I don’t know" — a capability no retrieval improvement can provide. That is a product decision, and the architecture follows from it.

Silent failure modes

A gate calibrated on too little data that never fires → an eval set with no headroom (7 of 8 solved at rank 1, so a real regression reads as noise) → tokeniser drift → index staleness after re-embedding → expansion adding noise on specific queries.

Why an interviewer asks

A litmus test for understanding that retrievers fail in complementary ways. The staff-plus probe is evaluation: "how do you know it got better?" This notebook shipped narration its own numbers contradict — spotting that is the judgement being tested.
